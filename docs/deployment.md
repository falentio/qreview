# Deployment

QR is deployed as an Astro Worker with Alchemy. The production stage serves
`https://qr.rindi.tech` and owns the following Cloudflare resources:

- D1 database `qr`
- KV namespace `QR_PUBLIC_PROJECTION`
- Astro Worker with the `qr.rindi.tech` custom domain
- Astro session KV namespace
- Alchemy-generated `BETTER_AUTH_SECRET`

The production stack is `Qr` and the production stage is `prod`. Alchemy state
is stored in Cloudflare through `Cloudflare.state()`.

## Prerequisites

- The `rindi.tech` zone is active in the Cloudflare account used by Alchemy.
- The Cloudflare profile has permission to manage Workers, D1, KV, custom
  domains, and DNS for the zone.
- The working tree contains the commit to deploy.
- The ignored `.env` file contains production application configuration.

Authenticate a dedicated production profile when possible:

```sh
vp exec alchemy login --profile prod --configure
```

Alchemy can also use the existing `default` profile. Profiles are stored
outside the repository under `~/.alchemy/profiles.json`.

## Production Environment

Set the following values in the ignored `.env` file:

```env
BETTER_AUTH_URL=https://qr.rindi.tech
```

`BETTER_AUTH_SECRET` is generated by `Alchemy.Random` and persisted in Alchemy
state. Do not add it to `.env`, delete the `BetterAuthSecret` resource, or clear
the production Alchemy state. The same generated value must survive every
redeploy so existing sessions remain valid.

Do not pass `.dev.vars` directly to a production deployment. It contains the
local Better Auth URL. If a value must be read from `.dev.vars` temporarily,
load it into the shell and override the URL explicitly:

```sh
set -a
. .dev.vars
set +a
export BETTER_AUTH_URL=https://qr.rindi.tech
```

## Plan And Deploy

Run checks before changing Cloudflare:

```sh
vp check
vp test
vp run test:integration
```

Preview the production stage:

```sh
vp exec alchemy plan \
  --stage prod \
  --profile prod \
  --env-file .env
```

Deploy after reviewing the plan:

```sh
vp exec alchemy deploy \
  --stage prod \
  --profile prod \
  --env-file .env
```

Use `--profile default` instead if the production credentials are stored in
the default profile. Do not add `--yes` until the plan has been reviewed.

The first Alchemy deployment may ask to bootstrap the Cloudflare state store.
Approve this only in the intended Cloudflare account. The state store is shared
by Alchemy stacks in that account.

## Existing Resources

Alchemy adopts old D1 migration history from Drizzle or Wrangler into its
`__alchemy_migrations` table. The old migration table is retained and frozen.
Do not manually run Wrangler migrations against the production database.

If Alchemy reports an unowned resource, verify the physical name and account
before retrying with `--adopt`:

```sh
vp exec alchemy deploy \
  --stage prod \
  --profile prod \
  --env-file .env \
  --adopt
```

`--adopt` is broad. It must not be used to claim resources from another
application or Cloudflare account.

If deployment fails with `databases per account (10)`, inspect the Cloudflare
D1 inventory before deleting anything. Delete only databases confirmed to be
unused, or request a higher account limit. Never delete a database based only
on a similar name.

## Custom Domain

The custom domain is configured in `alchemy.run.ts` only for the `prod` stage:

```ts
domain: stage === "prod" ? "qr.rindi.tech" : undefined,
```

Cloudflare creates the DNS record and certificate when the Worker custom domain
is reconciled. Do not create a competing CNAME for `qr.rindi.tech`. The parent
zone must already be active in the selected Cloudflare account.

The root domain and `www` are separate hostnames. Only `qr.rindi.tech` is
configured by this stack.

## Backfill KV

The optional backfill action copies current QR public projections from D1 into
`QR_PUBLIC_PROJECTION` with the configured seven-day TTL. Run it after the
initial production deploy if existing QR records need to be available through
KV:

```sh
ALCHEMY_PROFILE=prod vp run backfill-qr-public-projection -- --remote --stage prod
```

The command requires `--remote` and internally performs a forced Alchemy deploy
with `BACKFILL_QR_PUBLIC_PROJECTION=true`. It is safe to rerun after a public
projection schema change.

## Verification

Confirm that the stage has converged:

```sh
vp exec alchemy plan \
  --stage prod \
  --profile prod \
  --env-file .env
```

The expected result is `5 to noop` for the current stack.

Check the public routes:

```sh
curl -I https://qr.rindi.tech/
curl -I https://qr.rindi.tech/login
```

The root route should redirect to `/app`, and `/login` should return `200`.
If DNS was just created, wait for DNS and certificate propagation before
diagnosing the Worker.

Inspect the deployed resources without printing secret values:

```sh
vp exec alchemy state resources \
  --stack Qr \
  --stage prod \
  --profile prod \
  --env-file .env
```

## Rollback

Rollback application code by deploying a known-good commit:

```sh
git switch --detach <known-good-commit>
vp exec alchemy deploy --stage prod --profile prod --env-file .env
```

Return to the branch after the rollback. Database migrations are forward-only;
reverting application code does not undo a D1 migration. A migration rollback
requires a new forward migration designed for that change.

Do not run `vp run destroy --stage prod` as a rollback. The production stack's
resource removal policy includes resources that would be destructive to delete.
